Why ADE

Speed was never the hard part. Trust is.

The problem

Agents write code fast. Nobody trusts what they ship.

Teams spend their time checking, untangling and redoing agent work. Every session starts from zero, and the agent grades its own homework.

The promise

A delivery team that works like a good engineering team.

ADE plans, builds and reviews, it remembers, and nothing counts as done until the tests say so.

What you get

Five promises, each with its proof.

Every line below names the piece that does it, so you can check it in the source.

Verified

Nothing counts as done until the tests say so.

  • The verification command, agreed in the plan, gates Done. Green is Done; red is not.
  • No agent approves its own work. The reviewer, never the builder, runs the command and records its real output.
  • Review scales with risk: low gets the command only, medium one quick pass, high a thorough review plus one adversarial pass.

A team, not a chatbot

Roles with owners and boundaries, not one assistant doing everything.

  • 4 core roles from ade-method: product, architect, developer, reviewer.
  • 10 specialists from ade-agent-registry, loaded only when a task needs one.
  • An orchestrator that dispatches tickets to focus builders: ade dispatch.
  • Reviewers on a different model: by default the builder runs on Opus, the reviewer role on Sonnet.

It remembers

Every session starts from what is live, open and waiting.

  • The brain indexes the journal, each folder’s state and each project’s context and decision records, locally.
  • Hooks read that state back at session start and on every prompt, so each session knows what the others did.
  • Crash recovery: after a crash or a restart, bin/recover clears stale locks, repairs the event log, marks a dead agent’s ticket blocked and says how to resume it. Each repair is a line in the journal.

You stay in control

Agents do the work; the decisions that matter stay yours.

  • High-risk work waits for your approval, typed at your own terminal.
  • Secrets stay out of agents’ reach: a key goes from a hidden prompt to the hub’s key store (the macOS Keychain; on Linux, pass or a private file), never into an argument, a log or a Claude Code session’s environment.
  • ade-secrets, a local key store and terminal vault (ade-secrets vault), refuses to run inside an agent session.
  • Each customer kept separate: one hub per customer, with its own allowed models.

Works where you are

The same team in your terminal, on your phone and in the app.

  • ade ui: the orchestrator and the fleet in one tmux window, in any terminal, with a tab per focus agent. ade files and ade view show the hub’s files and code, read-only.
  • Telegram: message your orchestrator from your phone, paired to you alone.
  • Your tracker: ClickUp, Jira and Linear through the clickup, jira and linear plugins. Every change asks first.
  • Remote Control: the orchestrator and every focus session start with Claude Code’s Remote Control on, named after the hub or the folder.
  • The desktop app: frozen, still downloadable.
  • A Mac or an Ubuntu server: the hub runs on both. On a server, bin/server install checks SSH, the firewall and upgrades first and opens no public port.

How it works

Ticket, build, review, verified, done.

The whole loop, not just the code. Red at any gate goes back to the builder.

  1. Ticket

    A small story with acceptance criteria and a risk level. Write it yourself, or ask the orchestrator in plain words and it writes the ticket (bmad-ticket).

  2. Build

    ade dispatch starts a focus builder for ready tickets, as many at once as you allow, on the model you picked. It writes the failing test first, then the code.

  3. Review

    Scaled to risk. Anything touching secrets, sign-in, personal data, production or money is high risk, whatever its size, and gets the adversarial pass.

  4. Verified

    The reviewer, never the builder, runs the verification command and records its real output.

  5. Done

    Green is Done, and one dated line goes into the journal. Red goes back to the builder. There is no other path to Done.

Who it’s for

One delivery team, four ways in.

Developers

Hand off the ticket, keep the judgement.

ADE builds test-first on the model you pick, reviews by risk, and you merge only what’s green.

ade work <folder> --role builder opens a focus agent on that role’s model; ade roles shows which model each role gets.

Product managers

Write what you want in plain words.

Watch it get built from Telegram and approve what matters, without reading code.

The method has a section for people who don’t write code: ask in plain words, and the orchestrator writes the ticket and tells you when it is Done. From Telegram you ask for status, answer what it asks you to approve, and message a running focus agent.

Forward deployed engineers and consultancies

One hub per customer.

Their approved models only, their data stays put, every engagement document drafted.

ade hub new per customer; the hub runs only the providers it allows. The forward-deployed specialist and the fde plugin draft discovery, proposal, SOW, change request, design doc, status report and handover.

Support

Reproduce, investigate, draft the reply.

Nothing reaches a customer without your yes.

The support specialist reproduces, checks known issues, investigates read-only and drafts the reply. It asks before sending anything to a customer or changing their account.

Questions

Common questions

Is it safe to let agents do this?

Approvals: high-risk tickets wait until you approve them at your own terminal, typing the ticket’s reference back. Owner-only actions: nothing is sent to a customer, changed in an account or run on a live system without your yes, and ADE refuses to start Claude Code with its permission checks skipped. Secrets: keys go from a hidden prompt to the hub’s key store and never into an argument, a log or a Claude Code session’s environment. Isolation: one hub per customer; a provider you keep for your own work is refused in a customer’s hub.

Will I be locked in?

Open source: every repo is on GitHub under the MIT license. Any model: agents run through Claude Code, on Anthropic’s models or DeepSeek, focus agents and builders can run in the Gemini CLI, and each role can be pointed at another model; GLM and Muse Coming. Your own account: your Claude login or your own API key, on your own machine.

Isn’t this just prompts?

It’s a tested system, verified by its own test suites. Each repo has a verification command that CI runs on every pull request: bash tests/run.sh in ade-cli, ade-brain, ade-skills and ade-secrets, node scripts/validate.mjs in ade-method and ade-agent-registry. Every script in the hub has a test. The output at the top of this page is one of them.

What is Coming, and not here yet?

Marked Coming wherever it appears: the GLM and Muse providers, Gemini in ade setup’s live test, an Anthropic API key or DeepSeek for the orchestrator, and ade-secrets inside ade (ade key, ade vault).
