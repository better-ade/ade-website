A day with ADE

One engineer, four steps.

A fintech client, an agency project, a product of their own.

Step 1 · You

Say who you are.

The hub is built around your job.

  • Persona: one of 13 personas, like Staff Software Engineer, Tech Lead or Fractional CTO, set by ade hub new with your client and name.
  • Roles: 4 core roles from ade-method: product, architect, developer, reviewer. 10 specialists, like support and sysadmin, load when needed.
  • Yours: you approve high-risk work. The verification command decides Done.
Step 2 · Your context, tools and access

Context, tools, access.

On Claude or each role’s service, starting where the last session stopped.

  • Sign-ins: ade setup signs you in to Claude and GitHub.
  • Memory: each project’s state, decisions and journal.
  • Access: ade connect <service>: you sign in, the project keeps names only, every change asks.

Step 3 · Projects and customers

A focus agent per project.

Its own agent and context per project, so you run several tasks at once.

  • ade project add <path or git address>: a repo becomes a project folder.
  • ade work <folder>: its focus agent, seeing only that folder and its repos.
  • ade dispatch: ready tickets to focus builders, as many as you allow.
  • ade hub new per customer, each running only the models it approved.
Step 4 · Run it from the terminal or Telegram

At your desk or phone.

The same team, wherever you are.

  • Terminal: ade ui: the orchestrator plus a tab per focus agent.
  • Telegram: your own bot, locked to you, for status, messages and screenshots of proof.
  • Phone: ade web --tailnet, a read-only page.
  • Approvals at your terminal today; approval buttons in Telegram Coming
ADE Computer

One ADE Computer per engagement.

An ADE Computer is one machine: a mini PC, a compute instance or a container on your own Docker. For dedicated work, or several contracts in their own hubs.

Today: an Ubuntu desktop with ADE, VS Code, a terminal and database tools, per project or per task.

What is inside

Already set up.

  • Ubuntu 24.04 desktop in your browser, local only, with its own password.
  • ADE and Claude Code, git, node, bun, python3, tmux and a browser agents can drive.
  • VS Code, a terminal, DBeaver, DB Browser for SQLite, psql, mysql, sqlite3.
  • The guide first: the first terminal runs ade setup. No sign-in ships in the image.
How you use it

Per project or task.

  • Per project: named, and kept across restarts.
  • Per task: labelled with its ticket, or thrown away with its home on stop.
  • Several at once, each with its own home, password, address and network.
  • Save a state as a local image to start new ones.
  • Mini PC or compute instance (Ubuntu 24.04): the one-line install, then ade setup.
What it can reach

Honest about the wall.

  • Not given your home folder, keys or Docker socket; a project folder only when you name it.
  • A container, not a separate machine: it reaches the internet and, on Docker Desktop, your localhost services.
  • Agents inside have full rights. Give it nothing you would not give them.

Why ADE

Speed was never the hard part. Trust is.

The problem

Fast agents, no trust.

Teams redo agent work. Each session starts from zero, and the agent grades its own homework.

The promise

A real engineering team.

ADE plans, builds, reviews and remembers. Nothing is done until the tests say so.

How it works

Ticket to Done.

The whole loop. Red at any gate goes back to the builder.

  1. Ticket

    A small story with acceptance criteria and a risk level, by you or the orchestrator (bmad-ticket). Built on BMAD v6

  2. Build

    ade dispatch starts a focus builder. Failing test first, then code.

  3. Review

    Low: the command only. Medium: one quick pass. High (secrets, sign-in, personal data, production, money): a thorough review plus an adversarial pass.

  4. Verified

    The reviewer, never the builder, runs the command and records its real output.

  5. Done

    Green is Done, with a dated line in the journal. No other path.

Keys

Typed once, hidden.

A key goes in only at your own terminal, at a hidden prompt, in ade setup or bin/keys set <name>. Agents never see a value.

Never in a chat, a file or a command line. It lives in the hub’s key store: the macOS Keychain, or pass or a private file on Linux.

ade-secrets vault refuses to run inside an agent session.

Keys, in ade-brain’s README →
Memory

It remembers.

The brain indexes the journal, folder state, project context and decisions, locally. Hooks load it into every session and prompt.

After a crash, bin/recover clears stale locks, repairs the event log, blocks a dead agent’s ticket, says how to resume, and journals each repair.

Where it runs

Mac or Ubuntu server.

bin/server install checks SSH, the firewall and upgrades, and opens no public port.

  • ade files, ade view: hub files and code, read-only.
  • Remote Control on in every session.
  • The desktop app: frozen, still downloadable.

Questions

Common questions

Is it safe to let agents do this?

Agents ask before anything risky; nothing reaches a customer, an account or a live system without your yes. The paper has the security model.

Will I be locked in?

No. MIT open source, on your machine and accounts. Each role picks its service: Claude, DeepSeek or Gemini today, GLM and Muse Coming

Isn’t this just prompts?

No. CI runs each repo’s verification command on every pull request: bash tests/run.sh in ade-cli, ade-brain, ade-skills and ade-secrets, node scripts/validate.mjs in ade-method and ade-agent-registry. Every hub script has a test. One run is above.

Who pays for the AI models?

You do, directly, with your own account or key. ADE is free.

What is a hub?

One git repo per owner or client, made from ade-brain: context, memory, journal and the agents’ rules. Your code stays in its own repos.

Where do my prompts go?

Only to the AI services you choose. ADE runs no server and collects nothing; bot messages pass through Telegram.
